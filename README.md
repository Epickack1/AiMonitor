# AIMonitor

Приложение для отслеживания доступности моделей искусственного интеллекта в сервисе OpenRouter.
Консольная версия (ПР1–ПР3) дополнена веб-интерфейсом на Django (ПР5) с шаблонами и статическими файлами (ПР6); веб-интерфейс получает данные из базы SQLite SQL-запросами (ПР7).

## Назначение

OpenRouter даёт доступ к сотням моделей ИИ через единый API, но каждую модель обслуживают разные провайдеры, и любой из них может работать с перебоями. AIMonitor показывает, какие из выбранных моделей сейчас доступны, сколько провайдеров у каждой работает и каков их аптайм. Так перед подключением модели к своему проекту видно, стоит ли на неё рассчитывать.

## Целевая аудитория

- Разработчики, которые используют модели ИИ через OpenRouter в своих приложениях.
- Студенты и исследователи, которые выбирают модель, в том числе бесплатную.
- Администраторы сервисов с ИИ, которым важно заранее узнавать о сбоях моделей.

## Предметная область

Мониторинг доступности моделей ИИ. OpenRouter публикует каталог моделей и для каждой модели список провайдеров: их статус и процент времени без сбоев (аптайм) за последние 5 минут, 30 минут и сутки. На основе этих данных приложение определяет состояние модели. Дополнительно, при наличии API-ключа, модель можно проверить живым запросом с замером времени ответа.

## Объектная модель

Сущности предметной области представлены классами пакета `models`. Коллекции приложения — это списки объектов: `list[AIModel]` (список отслеживания и каталог), `list[CheckResult]` (история проверок).

### AIModel — модель ИИ

Модель из каталога OpenRouter.

Атрибуты:
- `id` — идентификатор в OpenRouter, например `openai/gpt-4o-mini`; свойство только для чтения (хранится в `_id`), потому что по нему с моделью связана история;
- `name` — название;
- `price` — цена токена запроса и ответа, `None`, если неизвестна;
- `FREE_SUFFIX` — атрибут класса, суффикс бесплатных моделей `:free`.

Методы:
- `is_free` (`@property`) — бесплатная ли модель;
- `matches(query)` — есть ли подстрока в id или названии;
- `to_data()` — данные для JSON;
- `from_data(data)` и `from_api(data)` (`@classmethod`) — создание объекта из JSON-файла и из ответа OpenRouter;
- `validate_id(model_id)` (`@staticmethod`) — проверка формата id;
- `__str__()` — «Название [бесплатная] (id)».

### Provider — провайдер

Компания, которая обслуживает модель.

Атрибуты: `name`, `status` (0 — работает, меньше 0 — сбой), `uptime_5m`, `uptime_30m`, `uptime_1d` (аптайм в процентах).

Методы: `is_working` (`@property`), `from_api(data)` (`@classmethod`), `__str__()` — строка таблицы провайдеров.

### CheckResult — результат проверки

Одна проверка доступности модели.

Атрибуты: `model` — объект `AIModel`, `status`, `uptime`, `checked_at`, `providers` — список объектов `Provider` на момент проверки.

Методы: `is_available` (`@property`), `from_providers(model, providers)` (`@classmethod`) — оценка доступности по провайдерам, `from_data(data, model)` (`@classmethod`), `to_data()`, `__str__()` — «время статус аптайм».

### ModelStats — статистика модели

Накопленная статистика проверок одной модели.

Атрибуты: `model` — объект `AIModel`, `checks`, `available`, `uptimes`.

Методы: `add(result)` — учесть проверку, `percent` и `avg_uptime` (`@property`), `__str__()` — строка таблицы статистики.

### Взаимодействие объектов

```
CheckResult
├── model ──→ AIModel
└── providers ──→ [Provider, Provider, ...]

ModelStats
└── model ──→ AIModel
```

`CheckResult` хранит ссылку на объект модели, а не только её id: данные модели доступны как `result.model.name`. Все проверки одной модели ссылаются на один и тот же объект `AIModel`. Статус модели вычисляется по её провайдерам: `CheckResult.from_providers(model, providers)`.

Операции над коллекциями остаются обычными функциями модулей: поиск и добавление моделей (`models/ai_model.py`), оценка статуса по списку провайдеров (`models/provider.py`), история, статистика и сортировка (`models/check.py`).

Декоратор `@timed` (`utils.py`) замеряет время работы функции. Он применяется к `send_test_prompt()` в живом тесте модели.

## Основные функции

1. Проверка доступности всех отслеживаемых моделей со сводкой.
2. Подробная проверка одной модели с таблицей всех её провайдеров.
3. Просмотр списка отслеживаемых моделей с результатом последней проверки и сортировкой по названию или по аптайму.
4. Поиск модели в каталоге OpenRouter, в том числе только среди бесплатных.
5. Добавление модели в отслеживание и удаление из него.
6. Живой тест модели: короткий запрос и замер времени ответа (нужен API-ключ).
7. Сохранение каждой проверки в историю (`data/history.json`).
8. Статистика доступности по истории: число проверок, доля успешных, средний аптайм, самая стабильная и самая проблемная модель.
9. Просмотр последних проверок выбранной модели.

Все данные сохраняются в JSON-файлах и загружаются при запуске. Некорректный ввод, отсутствующий или повреждённый файл данных не приводят к аварийному завершению программы.

## Как определяется статус модели

| Статус | Условие |
|---|---|
| Доступна | есть работающий провайдер, аптайм лучшего из них за 5 минут не ниже 90% |
| Нестабильна | провайдеры работают, но аптайм ниже 90% |
| Недоступна | ни один провайдер не работает |
| Не найдена | модели нет в OpenRouter или нет связи с сервисом |

Провайдер считается работающим, если OpenRouter сообщает для него статус `0`; отрицательный статус означает сбой.

## Веб-интерфейс (Django)

Веб-слой добавлен к проекту, а не заменяет его: view-функции получают данные из базы SQLite (раздел «База данных SQLite»), текущее состояние провайдеров запрашивают у OpenRouter и передают всё в шаблоны. Консольная версия `main.py` продолжает работать с JSON-файлами.

### Страницы

| Страница | URL | View-функция | Что показывает |
|---|---|---|---|
| Главная | `/` | `homepage.views.index()` | назначение приложения, сводка (моделей, проверок, последняя проверка), переходы к разделам |
| Модели | `/models/` | `watchlist.views.models_list()` | отслеживаемые модели, статус и аптайм последней проверки; поиск `?q=`, только бесплатные `?free=1`, сортировка `?sort=name` и `?sort=uptime` |
| Модель | `/models/<path:model_id>/` | `watchlist.views.model_detail()` | карточка модели с разработчиком, текущий статус и таблица провайдеров из OpenRouter, сводка и последние 10 проверок модели |
| История проверок | `/checks/` | `checks.views.history()` | последние 100 проверок, новые сверху; фильтр по дню `?day=` и статусу `?status=` |
| Статистика | `/checks/stats/` | `checks.views.stats()` | доля успешных проверок и средний аптайм каждой модели, самая стабильная и самая проблемная модель, проблемные модели, проверки по статусам и по разработчикам |

Если модели с указанным id нет в базе, страница модели возвращает код статуса 404. Несуществующий адрес также возвращает 404.

Для адресов без маршрута в корневом `aimonitor/urls.py` подключён обработчик `handler404 = "homepage.views.page_not_found"`: при `DEBUG = False` вместо технической страницы Django показывается собственная страница «404 – страница не найдена» с кнопкой возврата на главную. В `ALLOWED_HOSTS` указаны `localhost` и `127.0.0.1`.

### Динамический URL и конвертер `path`

id модели в OpenRouter содержит косую черту, например `openai/gpt-4o-mini`, поэтому конвертер `int` не подходит, а `str` не пропускает `/`. Используется конвертер `path`: адрес `/models/openai/gpt-4o-mini/` передаёт во view-функцию `model_id="openai/gpt-4o-mini"`.

### Django-проект и приложения

| Приложение | Предметная область | Классы ПР3 |
|---|---|---|
| `homepage` | главная страница, страница 404, статические файлы | — |
| `watchlist` | отслеживаемые модели | `AIModel`, `Provider`, `CheckResult` (текущий статус) |
| `checks` | история проверок и статистика | — (данные из SQLite) |

Пакет `aimonitor/` — конфигурация Django-проекта: `settings.py` (настройки, `INSTALLED_APPS`, язык `ru-RU`, часовой пояс `Europe/Moscow`), `urls.py` (маршруты верхнего уровня), `asgi.py` и `wsgi.py` (точки входа для серверов).

Маршрутизация двухуровневая: `aimonitor/urls.py` подключает функцией `include()` файлы `urls.py` приложений (`""` → `homepage`, `models/` → `watchlist`, `checks/` → `checks`). У каждого маршрута есть имя (`name=`), а у каждого приложения — пространство имён `app_name`.

Не путайте файл `models.py` Django-приложения с пакетом `models/` проекта: пакет содержит классы предметной области, а `models.py` приложений пока пуст — Django-модели появятся при переходе на ORM.

### Используемые функции ПР3

| Функция | Где используется |
|---|---|
| `fetch_providers()`, `CheckResult.from_providers()` | страница модели: текущий статус и провайдеры из OpenRouter |
| `count_working()`, `STATUS_AVAILABLE` | число работающих провайдеров; статус «Доступна» передаётся в SQL-запросы статистики параметром |
| `load_watchlist()`, `load_history()` | скрипт `db/import_json.py`: чтение и проверка JSON перед переносом в базу |

Страница модели запрашивает статус у OpenRouter при открытии, но не записывает его в историю: GET-запрос не должен изменять данные. Проверка с сохранением в историю, поиск по каталогу, добавление и удаление моделей и живой тест пока доступны только в консольной версии — в веб-интерфейсе они появятся вместе с формами и POST-запросами.

### Шаблоны Django (ПР6)

View-функции больше не собирают HTML в Python: они готовят контекст и вызывают `render()`, а страницу формирует Django Template Language. Функция `page()` из ПР5 удалена.

```
index() ──render()──▶ homepage/index.html ──{% extends %}──▶ base.html
                                                             ├─ {% include "includes/navigation.html" %}
                                                             └─ {% block title %}, {% block content %}
```

| Шаблон | Назначение |
|---|---|
| `templates/base.html` | общий каркас: `<head>`, Bootstrap, свой CSS, навигация, подвал, JavaScript; блоки `title` и `content` |
| `templates/includes/navigation.html` | навигационная панель с логотипом; активный раздел подсвечивается по `request.resolver_match` |
| `templates/includes/status_badge.html` | цветной бейдж статуса модели (`{% if %}` / `{% elif %}`) |
| `templates/includes/uptime.html` | аптайм в процентах или «нет данных» |
| `templates/404.html` | страница обработчика `handler404` |
| `homepage/templates/homepage/index.html` | главная страница |
| `watchlist/templates/watchlist/model_list.html` | список моделей, строка модели — `includes/model_row.html` |
| `watchlist/templates/watchlist/model_detail.html` | страница модели, карточка — `includes/model_card.html`; при отсутствии модели — ветка `{% else %}` и код 404 |
| `checks/templates/checks/history.html` | история проверок |
| `checks/templates/checks/stats.html` | статистика, карточки лидеров — `includes/stat_card.html` |

Каталог шаблонов уровня проекта подключён в `settings.py` параметром `DIRS: [BASE_DIR / "templates"]`, шаблоны приложений находятся благодаря `APP_DIRS: True`.

**Конструкции DTL:** `{% extends %}`, `{% block %}`, `{% include ... with ... %}`, `{% for %}` с `{% empty %}` (пустой список моделей, пустая история), `{% if %}` / `{% elif %}` / `{% else %}`, `{% with %}`, `{% url %}`, `{% load static %}` / `{% static %}`.

**Именованные маршруты и пространства имён.** В `urls.py` каждого приложения задан `app_name`: `homepage:index`, `watchlist:list`, `watchlist:detail`, `checks:history`, `checks:stats`. Все ссылки в шаблонах строятся тегом `{% url %}`, например `{% url 'watchlist:detail' model.id %}`; жёстко заданных адресов в шаблонах нет.

**Фильтры шаблонов:** `length` (число моделей и провайдеров), `default` (название модели или id, пустой статус), `floatformat` (аптайм и доля успешных проверок), `yesno` (бесплатная/платная), `first` и `last` (самая стабильная и самая проблемная модель), `truncatechars` (длинные названия в истории). Шаблоны автоматически экранируют данные из JSON и OpenRouter, поэтому ручной `escape()` больше не нужен.

**Статические файлы** (`homepage/static/homepage/`):

| Файл | Где используется |
|---|---|
| `css/style.css` | `base.html`: логотип, бейджи статусов, карточка модели, карточки статистики, кнопка копирования, подвал |
| `js/main.js` | `base.html`: текущий год в подвале и кнопки «⧉» — копирование id модели в буфер обмена |
| `img/logo.svg` | логотип в навигации и иконка вкладки |

Bootstrap 5.3 подключён через CDN и используется для базовой вёрстки: `navbar`, `table`, `card`, `btn`, `btn-group`, `badge`.

## База данных SQLite (ПР7)

Данные AIMonitor перенесены из JSON в реляционную базу `data/aimonitor.sqlite`. Работа с базой ведётся напрямую через SQL и стандартную библиотеку `sqlite3`, без Django ORM. Путь данных веб-интерфейса:

```
JSON ──db/import_json.py──▶ SQLite ──SQL──▶ sqlite3 ──▶ Django view ──context──▶ шаблон ──▶ страница
```

### Структура базы

Сущности предметной области — разработчик модели, модель ИИ и результат проверки. Один разработчик выпускает несколько моделей, у одной модели много проверок.

```
vendors 1 ──< models 1 ──< checks
```

**`vendors`** — разработчики моделей

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | первичный ключ |
| `slug` | TEXT NOT NULL UNIQUE | часть id OpenRouter до «/»: `openai`, `anthropic` |
| `name` | TEXT NOT NULL | название: `OpenAI` — из названия модели до «: » |

**`models`** — модели ИИ

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | первичный ключ |
| `openrouter_id` | TEXT NOT NULL UNIQUE | id в OpenRouter, например `openai/gpt-4o-mini` |
| `name` | TEXT NOT NULL | название модели |
| `vendor_id` | INTEGER NOT NULL | внешний ключ → `vendors.id` |
| `is_tracked` | INTEGER NOT NULL DEFAULT 1 | 1 — в списке отслеживания, 0 — удалена, но её проверки остались в истории |

**`checks`** — результаты проверок

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | первичный ключ, порядок проверок |
| `model_id` | INTEGER NOT NULL | внешний ключ → `models.id` |
| `status` | TEXT NOT NULL | «Доступна», «Нестабильна», «Недоступна», «Не найдена» |
| `uptime` | REAL | аптайм в процентах; **NULL допустим** — OpenRouter не сообщил аптайм |
| `checked_at` | TEXT NOT NULL | время `YYYY-MM-DD HH:MM`: такой формат сортируется и сравнивается как текст |

Признак «бесплатная модель» не хранится: он вычисляется условием `openrouter_id LIKE '%:free'`.

### Файлы

| Файл | Назначение |
|---|---|
| `sql/schema.sql` | `CREATE TABLE IF NOT EXISTS` для трёх таблиц с первичными и внешними ключами |
| `sql/queries.sql` | 15 проверенных SQL-запросов проекта с комментариями |
| `db/database.py` | `get_connection()` — подключение с `PRAGMA foreign_keys = ON`; `create_schema()`; `fetch_all()` / `fetch_one()` — параметризованный SELECT с `conn.row_factory = sqlite3.Row` |
| `db/import_json.py` | перенос `watchlist.json` и `history.json` в базу: `executemany()`, параметры `?`, `commit()`, при ошибке `rollback()` |
| `data/aimonitor.sqlite` | файл базы данных |

Создание базы и перенос данных (из корня проекта):

```bash
python -m db.import_json
```

Скрипт выполняет `sql/schema.sql`, очищает таблицы и заново переносит данные, поэтому его можно запускать повторно. Консольная версия по-прежнему записывает проверки в JSON: после проверок в `main.py` запустите импорт, чтобы веб-интерфейс увидел новые данные. JSON читается функциями `storage.py` из ПР3, некорректные записи пропускаются; модели, удалённые из отслеживания, попадают в `models` с `is_tracked = 0`, чтобы их проверки не потеряли внешний ключ.

Проверка запросов в SQLite CLI:

```bash
sqlite3 data/aimonitor.sqlite
```

### SQL-запросы (`sql/queries.sql`)

| № | Запрос | Вид | Где используется |
|---|---|---|---|
| 1 | отслеживаемые модели в порядке добавления | выборка, `ORDER BY` | `/models/` |
| 2 | модели по названию `COLLATE NOCASE` | выборка, `ORDER BY` | `/models/?sort=name` |
| 3 | дни, за которые есть проверки | выборка, `DISTINCT` | фильтр на `/checks/` |
| 4 | поиск по подстроке в id или названии | `WHERE ... LIKE` | `/models/?q=` |
| 5 | бесплатные модели | `WHERE ... LIKE '%:free'` | `/models/?free=1` |
| 6 | последние 10 проверок модели | `WHERE`, `JOIN`, `LIMIT` | страница модели |
| 7 | модель и её разработчик | `JOIN vendors`, `WHERE` | карточка модели |
| 8 | модели с последней проверкой | `LEFT JOIN`, подзапрос `MAX(id)` | таблица на `/models/` |
| 9 | история с названиями моделей за день и со статусом | `JOIN`, `WHERE`, `LIMIT` | `/checks/` |
| 10 | сводка: моделей, проверок, последняя проверка | `COUNT`, `MAX` | главная |
| 11 | сводка по модели: проверок, доля успешных, средний аптайм | `COUNT`, `SUM`, `AVG`, `ROUND` | страница модели |
| 12 | статистика каждой модели | `GROUP BY`, `COUNT`, `AVG` | `/checks/stats/` |
| 13 | проблемные модели | `GROUP BY`, `HAVING` | `/checks/stats/` |
| 14 | число проверок по статусам | `GROUP BY`, `COUNT` | `/checks/stats/`, фильтр на `/checks/` |
| 15 | разработчики: моделей и проверок | `JOIN` трёх таблиц, `GROUP BY`, `COUNT(DISTINCT)` | `/checks/stats/` |

### Запросы в Django-представлениях

Представления выполняют SQL через `fetch_all()` / `fetch_one()` из `db/database.py`: соединение настраивается `conn.row_factory = sqlite3.Row`, поэтому шаблоны обращаются к полям по именам — `{{ model.openrouter_id }}`, `{{ item.checks_count }}`. Результаты передаются в шаблоны через context.

Значения от пользователя никогда не вставляются в текст запроса: даты, статусы, строка поиска и id модели передаются параметрами `?` или `:имя`. Необязательные фильтры записаны в самом запросе — `(:day = '' OR substr(checked_at, 1, 10) = :day)`, а порядок сортировки выбирается выражениями `CASE WHEN :sort = 'name' ...`, поэтому текст запроса не меняется. Символы `%` и `_` в строке поиска экранируются (`LIKE ... ESCAPE '\'`) и ищутся буквально.

| Сценарий | Страница | Запросы |
|---|---|---|
| сводка на главной | `/` | 10 |
| список моделей с поиском, фильтром и сортировкой | `/models/` | 1, 2, 4, 5, 8 — объединены в один запрос `MODELS_SQL` |
| карточка, сводка и история модели | `/models/<id>/` | 6, 7, 11 |
| история проверок с фильтром по дню и статусу | `/checks/` | 3, 9, 14 и `COUNT(*)` с теми же условиями |
| статистика | `/checks/stats/` | 12, 13, 14, 15 |

## Формат данных

`data/watchlist.json` — список отслеживаемых моделей:

```json
[
  {
    "id": "openai/gpt-4o-mini",
    "name": "OpenAI: GPT-4o-mini"
  }
]
```

`data/history.json` — история проверок. `uptime` — лучший аптайм работающих провайдеров за 5 минут (при отсутствии данных — за 30 минут), `null`, если данных нет. Хранится не более 1000 последних записей.

```json
[
  {
    "model_id": "openai/gpt-4o-mini",
    "status": "Доступна",
    "uptime": 99.8,
    "checked_at": "2026-09-26 14:05"
  }
]
```

Записи с неверной структурой при загрузке пропускаются.

JSON используется для хранения, объекты — для работы программы. При загрузке `storage.py` создаёт объекты `AIModel`, а для каждой записи истории находит объект модели по `model_id` и передаёт его в `CheckResult`. Если модель уже удалена из отслеживания, её история не теряется: для неё создаётся объект `AIModel` с названием, равным id. При сохранении объекты превращаются обратно в словари методом `to_data()`, а вместо объекта модели записывается её `model_id`.

## Установка

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux / macOS
pip install -r requirements.txt
```

Для живого теста скопируйте `.env.example` в `.env` и впишите ключ с https://openrouter.ai/settings/keys. Остальные функции работают без ключа.

Перед первым запуском веб-версии создайте служебную базу данных Django и перенесите данные проекта в SQLite:

```bash
python manage.py migrate
python -m db.import_json
```

## Тесты и проверка кода

```bash
pytest -v
flake8 .
python manage.py check
```

Каталог `.venv` исключён из проверки flake8 в файле `.flake8`.

Тесты проверяют создание объектов и значения их атрибутов, методы и свойства классов, строковое представление, связь `CheckResult` с `AIModel`, определение статуса модели по провайдерам, историю и статистику, преобразование JSON в объекты и обратно, обработку повреждённых файлов и декоратор `timed`. Тесты `test_web.py` проверяют веб-интерфейс через тестовый клиент Django: разбор URL, коды ответа 200 и 404, содержимое страниц, сортировку, экранирование HTML, наследование `base.html`, подключение включаемых шаблонов и статических файлов, пустой список и собственную страницу 404. Для них временная база SQLite создаётся скриптом `db/import_json.py` из тестовых JSON-файлов, а запросы к OpenRouter подменяются, поэтому тесты не зависят от данных проекта и от сети. Проверяются также перенос данных и его повтор, контроль внешних ключей, поиск, фильтры, параметризация запросов и результаты группировки.

## План развития

Реализовано в ПР5:

- Django-проект `aimonitor` и три приложения: `homepage`, `watchlist`, `checks`;
- двухуровневая маршрутизация URL, динамический адрес страницы модели;
- view-функции и пять страниц с данными предметной области;
- навигация между страницами и оформление Bootstrap 5.3.

Реализовано в ПР6:

- страницы переведены на шаблоны Django: базовый шаблон, наследование, блоки и включаемые шаблоны;
- пространства имён URL и тег `{% url %}`, фильтры шаблонов;
- собственные статические файлы: CSS, JavaScript и логотип.

Реализовано в ПР7:

- база данных SQLite из трёх связанных таблиц, схема в `sql/schema.sql`;
- перенос данных из JSON скриптом `db/import_json.py`;
- 15 SQL-запросов в `sql/queries.sql`: выборка, `WHERE`, `JOIN`, агрегатные функции, `GROUP BY`, `HAVING`;
- страницы получают данные из SQLite параметризованными запросами; поиск и фильтры моделей и истории.

На следующих этапах планируется:

- подключение базы к Django ORM: модели Django вместо прямых SQL-запросов, консольная версия работает с той же базой;
- формы: проверка моделей с записью в историю, поиск по каталогу, добавление и удаление моделей;
- реализация пользователей с личными списками отслеживания;
- разработка REST API для получения статусов;
- уведомления о падении модели;
- контейнеризация приложения в Docker;
- настройка CI/CD.
